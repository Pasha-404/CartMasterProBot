# Задание для Terra: следующие доработки CartMasterProBot

## Что уже сделано

- Бот принимает Telegram webhook через `POST /webhook` и проверяет `X-Telegram-Bot-Api-Secret-Token`.
- Повторные Telegram update не обрабатываются дважды: в памяти хранится до 10 000 `update_id` на 15 минут.
- Нажатие inline-кнопки возвращает `answerCallbackQuery`; список обновляется в исходном сообщении, а не отправляется заново.
- Название товара ограничено 30 символами, а один список — 20 товарами. Эти пределы не дают превысить размер сообщения Telegram.
- Внешние секреты остаются только в `BOT_TOKEN` и `WEBHOOK_SECRET` на VPS.
- GitHub Actions собирает и тестирует каждый push в `master`, затем по SSH запускает `git pull --ff-only`, Maven-сборку и перезапуск systemd-сервиса на VPS. Подробности — в `DEPLOY_VPS.md`.

Не возвращать эти проблемы и не менять webhook на long polling.

## P1: отдельная миграция TelegramBots

Проект всё ещё использует устаревший `TelegramWebhookBot` из `telegrambots-spring-boot-starter 6.9.7.1`. Это работает, но требует отдельной миграции на современный webhook starter библиотеки TelegramBots.

Требования:

- сохранить webhook-режим и путь `/webhook`;
- сохранить проверку secret header до обработки update;
- не создать второй Spring bean или второй controller для webhook;
- оставить обработку `answerCallbackQuery` и редактирование списка;
- не логировать token, webhook secret, тексты сообщений, chat ID и user ID;
- провести миграцию отдельным небольшим изменением с тестами и `mvn clean package`.

Не менять версию библиотеки вместе с новой бизнес-логикой или БД.

## P2: решения владельца продукта

### Постоянное хранение списков

Сейчас списки живут только в памяти и очищаются после рестарта приложения. Сначала спросить владельца, нужно ли хранить их после деплоя и рестарта.

Если нужно, предложить минимальную схему PostgreSQL, миграции и атомарное перемещение товара в купленные. Если не нужно, оставить это ограничение явно описанным в документации.

### Списки в групповых чатах

Сейчас ключом списка служит `chatId`: все участники группы работают с одним списком. Сначала уточнить, это ожидаемый семейный сценарий или у каждого участника должен быть личный список по паре `chatId + userId`.

После решения добавить тесты для групп и личных чатов.

## P3: проверка фактического VPS

Проверить, что variables GitHub соответствуют реальному VPS: SSH-пользователь, каталог Git-репозитория, имя systemd-сервиса, его `ExecStart`, ограниченные права sudo и host key. Не подставлять предполагаемые значения.

После предоставления read-only SSH-доступа или вывода этих настроек обновить `DEPLOY_VPS.md` так, чтобы инструкция описывала конкретный работающий сервер, а не шаблон.
